THE WEB DASHBOARD · IN ACTION

Your builds, one browser tab away.

bitloom --web opens the dashboard on the build service. Close the tab, open it on another machine through an SSH tunnel, or switch to the terminal: the queue, the history and the running build stay where they are.

Follow and diagnose

Live output with search and an errors-only view, progress and ETA, then a Toaster-style summary, sstate reuse, warnings, timings and a comparison with the previous run. A failed build starts with the diagnosis of its real cause.

What is in the image, and why

Browse what you built, file by file, with the package and recipe behind each one and what pulls it in, see what starts at boot, what listens on the network and where the space goes, and read the board's device tree. Which recipe installs… answers for any file; Change it opens the append, starting from the file as it is on the device.

Pick an image, press b

The target field lists the image recipes in your layers, the kas target and what is already built first. Any recipe, or several, can still be typed.

Recipes by layer

Every layer with its counts, folders that open on demand, filters for recipes, images, appends, classes and kas files, and a search that keeps the structure.

SBOM, CVEs and the CRA

SBOM quality gauges, vulnerabilities from sbom-cve-check, cve-check and Grype with Markdown, HTML, CSV, JSON and SARIF exports, release support and CRA readiness.

Studio, step by step

Pick what to create, then walk through it: every option says what it means, the preview shows where the files go and what they contain, the review lists exactly what Create will do, and the last screen offers what comes next.

Scarthgap → Wrynose, guided

Every rule of the official migration guides checked on your files, the mechanical changes applied with a diff and undo, and the new kas file written next to the old one with its own profile. The current build keeps working while you try the new one.

Write BitBake without guessing

Completion from your own layers (variables with their documentation, classes, overrides, recipes, features), and the mistakes a parse would hit shown as you type. bitloom --lint does the same in CI.

Best practices, your rules

See how far your layers follow the Yocto advice, where they do not and how to fix it. Switch rules off, change their weight, add your company's own, and fail CI with bitloom --practices.

Any project, set up in a minute

Point it at a folder: kas files, Poky checkouts and YML=… ./run_kas.sh build launcher scripts become profiles, one per product, with the build folder found for you.

DAILY WORKFLOWS

Work through the problem.

01 · Build an image or one recipe

Choose a profile, enter a target, press F2 and filter the action list. Queue a normal build, compile task, dry run or SDK. The history row records the original profile and exact exit result.

02 · Investigate a failed task

Select the failed history row. Toggle Errors only or search a phrase with context. Open Task logs for the recipe's own compile/fetch log. Export the complete original log or open a concise build report.

03 · Develop and finish a recipe

Find a recipe in Layers & recipes, choose Modify, and use devtool build while editing its sources. Finish into the selected layer when ready. Interactive commands use your real terminal.

04 · Stop a build intentionally

Let finish leaves the build running. Graceful stop sends one SIGINT to a host client or a newly managed container and waits. Force terminates and offers clean for observed active recipes. Owned kas-container force stops record the exact container result; external wrappers require server verification before recovery.

05 · Inspect shared state and downloads

Scan the cache, filter files, select an age and review the concrete prune plan. No automatic deletion. Externally shared caches require coordination. Fetch tasks validate recipe sources with BitBake's checksums.

06 · Compare configurations and releases

Resolve two environment snapshots for a target and compare their values. Load dependency graphs from host or container and inspect reverse dependencies. Inspect buildhistory diffs and local repository versions. Keep release builds in separate profiles/directories.

NEW CONNECTED WORKFLOWS

Ask why. Keep the evidence.

Explain rebuild signatures, trace an image file to its recipe and packagegroup, inspect runtime preflight, compare build snapshots and export redacted reproducibility references. Review source changes before devtool finish/reset. Advisory locks coordinate cooperating cache users; unproven references never trigger automatic removal.
